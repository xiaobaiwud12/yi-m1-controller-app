# YI M1 协议参考（开源客户端实现依据）

本文档是 `app/` 下客户端实现的**唯一权威依据**。每条都标注来源与置信度。
**不要凭猜测在这里添加内容**——错误的值会让相机静默拒绝命令。

置信度分级：
- **【已验证】** —— 来自社区逆向实现或固件反汇编，可复核
- **【高置信】** —— 有强证据但未端到端实测
- **【待确认】** —— 需真机或原版 APP 交叉验证

来源代号：
- `[RE]` = 社区逆向项目 `bullbin/xiaoyi_m1_re_liveview`（MIT），本项目只取其常量表
- `[FW]` = 对本机相机固件镜像的分析
- `[APK]` = **官方 APP 3.1.6 反编译**（包名 `com.xiaoyi.mirrorlesscamera`）——反编译产物不随本仓库分发
- `[HW]` = **真机实测**（维护者的一台 M1，固件 `1,3.1-cn ,M1CN,0.0`）

> **证据优先级**：`[APK]` 与 `[HW]` > `[RE]`。
> 社区逆向有四处与实测不符，见 §2.6。

## 1. 总体架构

相机有**两条独立控制通道**，外加一条视频回传：

| 通道 | 用途 | 载体 |
| --- | --- | --- |
| **BLE** | 配对、开 Wi-Fi、**对时**；另有一套完整遥控通道 | GATT 特征读写 |
| **HTTP** | 全部 45 条控制/查询命令 | `GET http://192.168.0.10/?data={json}` |
| **UDP 54321** | 实时取景回传（800×600 JPEG + 参数） | 广播/单播数据报 |

**必须先走 BLE**：相机默认不广播 Wi-Fi，是 BLE 命令把它打开的。而且相机的 Wi-Fi
是**单客户端 AP**，只有第一个连上的设备能拿到 IP。

## 2. BLE 协议【已验证】`[RE]`

### 2.1 服务与特征

主服务：`41106dd9-25ad-477b-a884-5038b6de4649`

| 特征 | 方向 | 用途 |
| --- | --- | --- |
| `41106da0-…` | 写 | 发起配对 |
| `41106da7-…` | 通知 | 配对结果（token 或空） |
| `41106da9-…` | 写 | 解除配对 |
| `41106da1-…` | — | **真机上不存在**（官方 APP 源码里声明了该字段但容忍缺失；见 §2.6） |
| `41106da2-…` | 读 | 固件/型号信息 |
| `41106da4-…` | 写 | 开始会话（认证） |
| `41106da5-…` | 写 | 开/关 Wi-Fi（`"ON"`） |
| `41106da6-…` | 读 | 读取 Wi-Fi 凭据 |
| `41106dac-…` | 写 | **对时** |
| `41106dad/ae/af-…` | 写/通知 | 仅在部分固件存在（见 2.5） |

标准设备信息特征（`0x2a00/2a01/2a24/2a29`）也在。

### 2.2 握手流程（严格按序）

```
1. 读 41106da2  →  "1,M1,M1INT,1.1"
                     │  │   │      └─ 镜头固件版本
                     │  │   └──────── 区域标记（M1INT=国际版，M1CN/M1=国内版）
                     │  └──────────── 机身固件/型号
                     └─────────────── BLE 协议版本

2. 订阅 41106da7（通知）
   写   41106da0  →  "1,<key>,android"
                     key 为 0..99998 的随机整数
                     相机屏幕会弹出确认框，需人工按 Accept

3. 通知回调收到 token（空载荷 = 被拒绝）

4. 写 41106da4  →  "1,<key>,<crc32>"
                     其中 crc32 = zlib.crc32(ascii("1" + key + token))

5. 读 41106da6  →  "<ssid>,<passkey>"

6. 写 41106da5  →  "ON"          打开相机 Wi-Fi
```

### 2.3 安全性说明（必须写进文档与 UI）

**这个协议没有真正的安全机制**，不是一个可以被"修好"的实现细节：

- 配对密钥是 **0..99998 的明文整数**，无密钥交换、无加密；
- 会话校验值就是 **CRC32**，不是 MAC、不是签名——它能过是因为相机只做格式检查，
  **它不证明任何身份**；
- 配对确认是**相机屏幕上的物理按键**，这是唯一真正的授权环节；
- 相机**同时只保存一个配对**，新客户端配对会**静默作废官方 APP 的配对**。

因此：不要把它描述成"安全配对"。它是明文协议，物理确认才是授权。

### 2.4 对时【高置信】`[FW]`

- 相机**没有 RTC**。时间只是 RAM 里两个 6×int16 结构（年/月/日/时/分/秒），
  **断电即丢**。固件内 `rtc`/`RTC`/`/dev/rtc`/`settimeofday` 等 **0 命中**。
- 特征 `41106dac` 的处理体在 `IMG1` 文件偏移 `0x14E5EC`（备用设置点 `0x14DDC4`）：
  校验 `ctx+0x20 == 1` → 从 BLE 接收缓冲取 **ASCII 十进制串** → `strtol`（base 10）
  → 拆成 6 段日历字段 → 投递系统事件 `0x7A`。
- 推断载荷为 **Unix 纪元秒**（依据：base-10 解析 + 随后分解为日历 6 段）。
- **【已确认】`[APK]`** 官方 APP 的实现是 `(System.currentTimeMillis() / 1000) + ""`，
  即**纪元秒的 ASCII 十进制串**——与固件分析完全吻合，推断成立。
- **HTTP 无法对时**：45 条命令无时间项，两个设置点都只读 BLE 缓冲。

> **行动含义**：客户端**必须**在每次开机后对时，否则每张照片的 `capture_date` 全错。
> 这是"现代工作流"里性价比最高、且零固件风险的一步。

### 2.5 可选特征【已验证】`[APK]` `[HW]`

真机确认 `41106daf` 与 `41106dae` **都存在**。官方 APP 在发现 `41106daf` 后
会订阅它、订阅 `41106dae`，并向 `41106dad` 写入 `"3"`。

`41106dae` 的通知载荷是**镜头信息**，格式 `"3,<...>,<lensType>,<lensVersion>"`
（用 `,` 分割，首字段为 `"3"`）；`41106daf` 是**相机主动通知**，
载荷 `"ac,<code>"`，`code` 为 3/7/8/9，分别对应断开/相册/取景等状态切换。

### 2.6 社区逆向与实测不符之处【已验证】`[HW]`

| 社区记录 | 实测结果 |
| --- | --- |
| `41106da1`（RESPONSE_TOKEN）存在 | **不存在**（官方 APP 也容忍其缺失） |
| `41106dae` / `41106daf` 仅部分固件有 | **都存在** |
| 配对可用带响应写入 | **必须用无响应写入**；带响应写入返回应用层错误 `0x80` |
| 固件信息第 2 字段是区域标记 | 第 2 字段是**固件版本串**（含尾部空格），**第 3 字段**才是区域 |

### 2.6.1 ⚠️ 写入方式必须**按平台协商**，不能硬编码【已验证 `[HW]`】

相机的特征**只声明 `write`**，**不声明 `write_no_response`**。

| 平台 | 行为 |
| --- | --- |
| **Windows**（协议最早在此验证） | 不校验声明属性，`write-without-response` 照样成功 |
| **Android** | **严格校验**。`flutter_blue_plus` 在写到射频之前就抛错：<br>`PlatformException(writeCharacteristic, The WRITE_NO_RESPONSE property is not supported by this BLE characteristic)` |

**客户端必须在运行时读取特征的真实属性再决定写入方式**：

```
offers writeWithoutResponse == true  ->  用无响应写入
                                          （优先，因为固件在某些路径上
                                           对带响应写入回 0x80）
否则                                  ->  用带响应写入
                                          （没有别的选择，Android 会直接
                                           拒绝未声明的写法）
并记住哪种方式成功，后续复用
```

> **教训**：在 Windows 上验证过的 BLE 行为**不能直接搬给 Android**。
> 属性校验强度是两个平台之间最容易踩的差异。
>
> 实现在 `app/lib/transport/flutter_ble_transport.dart`：按属性协商、
> 失败时尝试另一种写法、并把**相机自报的特征属性**写进可在界面上查看的
> 诊断日志（连接页右下角的终端图标）。这类问题只有看到真实属性才能定论。

> **待确认**：本相机接受**带响应**写入这一点尚未在真机验证。
> 若带响应写入返回 `0x80`，说明该特征确实只支持无响应写入，
> 那么 Android 上就需要在插件层绕过属性检查，而不是回退写法。

### 2.7 配对被拒时的判读【已验证】`[APK]` `[HW]`

配对成功与否**只看通知载荷**：

| 通知载荷 | 含义 | 官方 APP 的表现 |
| --- | --- | --- |
| 非空字符串 | 成功，该串即 token | 继续开会话 |
| **空** | **相机拒绝了配对** | 错误码 110 → 界面显示 **"已忽略相机端蓝牙配对"** |

**实测现象**：本机 `M1CN`（国内版）对**所有**配对载荷变体
（不同协议号、不同客户端名、不同长度）都返回空通知。

同时，写 `41106da0` / `41106da9`（解绑）/ 读 `41106da6` 都会返回
应用层错误 **`0x80`**（相机的"当前状态不允许"通用错误）。

**已排除的原因**：
- 不是载荷格式（连最短的 `"12345"` 也被拒）；
- 不是写类型（无响应写入被接受，带响应报 `0x80`）；
- 不是缺特征（所需特征都在）；
- 不是服务未发现（GATT 表完整枚举成功）。

**最可能的原因（待真机确认）**：
1. **相机仍绑定着别的设备**。相机只存一个绑定；而官方 APP 的解绑要求
   **已完成会话**，所以遗留绑定会形成死锁，**只能在相机侧清除**
   （相机菜单里的"忘记设备/解除绑定"，或恢复出厂设置）。
2. 配对时相机需要处于特定界面状态（官方 APP 会提示"请查看相机屏幕提示"）。
3. 配对可能需要在 SD 卡上写数据（官方 APP 有"请确保相机开机并插入SD卡"提示）。

> 官方 APP 的界面文案（`res/values-zh-rCN/strings.xml`）已提取，可用于对照排查：
> `binding_check_camera`="请查看相机屏幕提示"、`binding_ble_ignored`="已忽略相机端蓝牙配对"、
> `binding_ble_wrong_area`="相机与App版本不兼容"、`binding_prompt_switch`="请确保相机开机并插入SD卡"。

## 3. HTTP 协议【已验证】`[RE]` `[FW]`

### 3.1 请求形态

```
GET http://192.168.0.10/?data={"command":"<命令名>","<参数>":"<值>",...}
```

- **全部走 GET**（因此**没有 CSRF 防护**）
- **无鉴权**：三镜像中 Digest/Basic 相关的全套字面量**零引用**，
  无 password/token 字面量，无来源 IP/MAC 比较
- 错误码集合为 400/401/404/405/413/500/503/505，**无 501**；不支持的方法返回 405
- `[FW]` 服务器是**自研状态机**，不是 GoAhead（GoAhead 全套字面量零引用），
  实现在 `IMG1` 文件偏移 `0x410000–0x41A000`

### 3.2 命令清单

**共 45 条**，Dart 常量见 `app/lib/protocol/http_commands.dart`——该文件是这些命令的完整、可读形式。

> ⚠️ handler 偏移随固件版本变化（实测各镜像不同）。不要凭记忆里的偏移定位，
> 命令名本身就够用——客户端只按名字发命令。

### 3.3 官方 APP 未使用的命令（★ 客户端可解锁的能力）

**共 13 条**（原版 APP 逆向交叉验证：45 条中实际用到 32 条）。

| 命令 | 能力 |
| --- | --- |
| `VideoRecordingStart` / `VideoRecordingStop` | **遥控录像**（官方 APP 完全没有） |
| `RCVideoFormatSet` | 录制档位，含 `4K_30`/`4K_24`/`4K_30_LOW`/`2K_30`/`2880_24`/`FHD_60` 等 |
| `RCEisSwitchSet` | 电子防抖 |
| `RCVANoiseReduceSet` | 数字降噪 |
| `RCVASwitchSet` / `RCVAVolSet` | 视频音效开关/音量 |
| `StartMovieStream` / `StopMovieStream` / `PauseMovieStream` / `ResumeMovieStream` | 推流细控（可用于"同步相册时暂停取景"） |
| `ChangeCurrentFrame` | 语义未知 |
| `CloseAP` | 关闭相机软 AP（官方 APP 改用 `RCStopRemoteCtl` + 手动断 Wi-Fi） |

> ⚠️ **修正**：早先版本把 `RCCancelShooting` / `RCCancelShooting1` 列为"未使用"，
> **这是错的**——原版 APP 确实会发这两条（超时分别为 10s / 60s）。
> 真正未使用的就是上表 13 条。

（`ProcessMovieStream` 未出现在 45 条表中，勿引用。）

### 3.3.1 `GetFileList` / `GetFileInfo` 的 404 不是"端点不存在"【已验证】

这两条命令**需要参数**，缺参数时 handler 返回 −1 且**不写响应体**，
HTTP 层便呈现为 404：

| 命令 | 必需参数 |
| --- | --- |
| `GetFileList` | `range_start` + `range_end`（**1 基，每页 60**） |
| `GetFileInfo` | `path` |
| `GetFile` | `path` + **`resulotion`**（固件里的拼写，取值 `Original`/`MidThumb`/`Thumbnail`） |

`GetFile` 成功时**响应体就是原始文件字节**（非 JSON）。

### 3.4 危险命令（客户端应拒绝或强制二次确认）

| 命令 | 风险 |
| --- | --- |
| `UpdateFW` | 从 SD 卡刷固件 → **可致变砖** |
| `UpdateLenFW` | 刷镜头固件 |
| `UploadML` | 向 `/XIAOYI/MASTER/%s` 写文件 |
| `DeleteFile` | 删除文件，取值含 `ALL`，**无二次确认** |
| `DeleteMLFile` | 删除文件 |
| `CloseAP` | 关闭 Wi-Fi。**不是单向门 —— 见下方 ⚠️** |

> ### ⚠️ 更正（2026-09-16）：关掉 Wi-Fi 之后**能**再打开，走 BLE
>
> **此前这里写的是"无对应的 `OpenAP` → 关了可能无法用 HTTP 再开"。前半句对，
> 后半句错，而且这条误导让好几个人（包括我）把 `CloseAP` 当成了不可逆操作。**
>
> **Wi-Fi 的开关根本不在 HTTP 上，它在 BLE 上**：
>
> ```
> 特征 41106da5-25ad-477b-a884-5038b6de4649    ← 名字就叫 WIFI_TOGGLE
> 写 "ON"   → 打开（app/tools/client.py:392，实测可用）
> 写 "OFF"  → 关闭（同一个特征，toggle 语义）
> ```
>
> **而这一条是实测出来的，不是推的**：`ble-wifi` 与相机网络栈卡死后的三次恢复，
> 全都是在 **PC 不在相机热点上**时执行的 —— 也就是走 BLE。
>
> ### 真正的边界条件（比原来那条更值得记住）
>
> **BLE 那条路要求配对有效。** 而相机**只保存一个配对**，且新配对会顶掉旧的。
> 所以：
>
> | | `CloseAP` 之后 |
> |---|---|
> | **配对完好** | ✅ `WIFI_TOGGLE = "ON"` 重开 |
> | **配对被别的设备顶掉** | ❌ **两条路同时断** —— HTTP 侧没有 `OpenAP`，BLE 侧没有配对 |
>
> **所以风险不是"关了就回不来"，而是"关的时候有一条退路，而那条退路依赖一个会被顶掉的凭据"。**
>
> **推论**：要关相机 Wi-Fi，**走 BLE 写 `WIFI_TOGGLE = "OFF"` 比走 HTTP `CloseAP` 更好** ——
> 开关同一条通道、同一个特征，语义对称，而且不引入一条只走 HTTP 的路径。

`Model`/`Attachment`/`ColorMode`）。

## 5. 已知限制（必须体现在 UI）

| 限制 | 后果 |
| --- | --- |
| Wi-Fi 只服务**一个**客户端 | 手机连上后电脑就连不上 |
| 相机是 **AP**，不能接入家庭网络 | **无法自动上传到 NAS/云**（固件级限制：无 DHCP 客户端） |
| 固定 IP `192.168.0.10` | 与 VPN/多网卡冲突；密码每次会话随机，需"忘记网络"重连 |
| **无鉴权 + GET** | 同网段任何人可控制相机 |
| **无 RTC** | 开机必须对时 |
| 配对会被新客户端覆盖 | 官方 APP 与第三方客户端不能同时配对 |
